# M7: strict representations and native builtins

The milestone after M6, written up 2026-10-05 from the progress log after the work landed
(the other milestone plans were written before their work started; this one wasn't planned
as a milestone, it grew out of M6's open items and Paul's requests, so it is told in the
order it happened). The detail of each step, with the measurement tables, is in the
[progress log](progress.md) under the section the step names. Every step is in the one M7
commit.

**Goal.** Take the exits out of the data: the structures native code meets most (lists,
text, bytes, arrays, refs, numbers) are strict and have native operations with no fallback
to the interpreter, so that library code that uses them runs natively from end to end. And
make what the JIT does itself (allocation, the generated code's shape, the generator) cost
what it should.

Where it ended: 238 of the 602 builtins have native implementations ([builtins.md](builtins.md)),
which is all of Int, Nat, Float, Text, List, the arrays, refs and universal comparison, and
Bytes except compression; a `Text`, a `Bytes` and a `List` are strict finger trees; native
code bumps the allocation pointer inline; the generator builds packed text with no
laziness. On `jitSuite` every row is faster than the interpreter, from 3× to 196×; on the
broad `suite` nothing is slower than the interpreter beyond noise, and the rows the JIT
doesn't speed up are the ones that spend their time in Haskell (serialization, JSON, `Map`,
`Stream`, the ability-based `fib`s). The closing tables are at the end of this document.

## Order of work

- [x] **1. Lists on a strict finger tree** (`Unison.Util.Deque`, 2026-10-02). M6 had put
  lists on a strict structure of Paul's; this step replaced it with a finger tree written
  beside it as `Deque2` (a prefix and suffix digit of up to ten items as strict lists, a
  strict middle of nodes that are eight leaves inline or an array of two to eight children),
  tested against `Data.Sequence` with an invariant checker after every step, benchmarked
  against it, then swapped in and given the name. Every list primitive became a C port of
  the Haskell operation with no fallback: cons, snoc, uncons, unsnoc, `at`, the views and
  splits that list patterns compile to, `++`, `take`, `drop`, list literals. Against
  `Data.Sequence` at 10,000 elements: snoc 7.5 ns against 10.3, uncons 5.3 against 11.5,
  lookup 32 against 96; `append` of two large pieces is the one loss. `List.map increment`
  0.23× and `List.foldLeft` 0.19× of the interpreter's time. See "The list representation".
- [x] **2. Text and Bytes on the same tree** (`Unison.Util.Rope`, 2026-10-02). The rope
  of chunks under `Text` and `Bytes` became the Deque's finger tree with chunks for elements
  and sizes counted in characters or bytes, sharing the Deque's middle below the top level;
  written as `Rope2` beside the size-balanced tree, benchmarked, swapped in (Paul's plan).
  Threshold 64 after trying 16, 32 and 128. Appending short pieces 3 to 4× faster, walking
  by character 2×; appending two large texts is slower (the finger tree packs the digits at
  every level) and is left to the ideas. The C text helpers are ports of the top level over
  the list helpers' functions. See "The text representation".
- [x] **3. Bytes natively** (2026-10-02). The C text section became a "Ropes" section
  parameterised by a `RopeKind` (the constructors, the threshold, where a chunk's fields
  are, whether counts are characters), so the bytes helpers are the text helpers with
  another kind; `Bytes.at`, `flatten` and universal `==` on two texts or two bytes with them.
  Appending two bytes 10000 times 1.03 ms interpreted to 310 µs. See "The bytes helpers".
- [x] **4. The rest of Text and Bytes** (2026-10-03, Paul: "finish converting all Text and
  Bytes builtins"). `uncons`/`unsnoc`, numbers to and from text (`Float.toText` as Haskell's
  `show`: shortest digits that read back), `pack`/`unpack`, `indexOf`, the orderings and
  universal `<`/`<=`/`compare` on texts and bytes, and the pure foreign functions
  (`Text.repeat`, `reverse`, the ASCII case mappings, UTF-8 both ways, `Char.toText`, the
  Bytes number encodings and reads, base 16/32/64). Each helper answers "not handled" for
  what it can't decide exactly (a number in a form the Haskell lexer reads differently, a
  non-canonical encoding, a non-ASCII case mapping) and the call-out does it. Bytes
  literals are native through `Bytes.fromList`. The Text patterns, compression and
  `Link.toText` stay call-outs. `Nat.toText` and back 10000 times 7.95 ms to 803 µs. See
  "The rest of Text and Bytes".
- [x] **5. Untagged pointers in strict fields** (2026-10-03, a crash found by the Bytes
  tests). The interpreter stores a static constant such as `noneClo` as the untagged address
  of its CAF, and native code copied such a pointer into a `Pack`'s strict field; GHC's
  optimized code reads a strict field without checking the tag. `requireTagged` now checks
  the pointer tag before every store into a strict field and takes the slow path for tag 0,
  as the read side already did. See "A fixed crash".
- [x] **6. Inline bump allocation** (2026-10-03, budget folded in 2026-10-04). Native
  code and the C helpers bump a copy of the current allocation block's free pointer (the
  register table's `rCurrentAlloc`, the block `allocate` uses) against a limit and call
  `allocate` only on a miss, as compiled Haskell does with `Hp`/`HpLim`; the trampoline
  syncs the pointer and charges the thread's allocation counter. The allocation budget is
  an address, `budget_end`, and the limit is the nearer of it and the block's end, so the
  fast path is one compare. Allocation-heavy rows 1.1× to 1.5× faster (`Mutate a Ref` 52 µs
  to 34 µs), `-DS` heap checks pass. See "Inline bump allocation".
- [x] **7. Floats, `pow` and the casts** (2026-10-04). Every Float operation, `Int.pow`,
  `Nat.pow`, `toFloat` and the `CAST` behind the representation coercions, bit for bit
  GHC's results: libm for the transcendental functions, saturating conversions, `rint` for
  `round`, GHC.Float's own `ceiling`/`floor` arithmetic, `Ord Double`'s `min`/`max`, a port of
  GHC's case-defined `atan2`. All of Int, Nat and Float native. The float loop 33.7 ms to
  1.01 ms. See "Floats, pow and representation casts".
- [x] **8. Private copies and re-entry batches** (2026-10-04, from the batching discussion
  in the ideas doc). A module that calls an already compiled small callee (estimated work
  per call under `UNISON_JIT_COPY`, not recursive) compiles it again as a private, internal
  copy, so the call is direct and LLVM inlines it; every copy in the test transcript was
  inlined away. Re-entry functions asked for on demand are held for `UNISON_JIT_REENTRY_WAIT`
  ms and compiled as one module. Test transcript with `THRESHOLD=1`: 185 modules to 93,
  16.2 MB of IR to 13.3 MB. See "Private copies and re-entry batches".
- [x] **9. Arrays and Refs** (2026-10-05). Every array builtin (mutable and immutable,
  pointer and byte arrays, every width and byte order, `copyTo!`, both freezes,
  `toBytes`/`fromBytes`, the `Scope` and `IO` constructors, pinned arrays), `Scope.ref`,
  `Ref.readForCas`, `Ticket.read` and `Ref.cas`, as C helpers that reproduce the Haskell
  bounds arithmetic exactly (a failing check goes to the interpreter, which raises) and build
  the heap objects as the RTS primops do (dirty info pointers, card tables, `allocatePinned`,
  `casMutVar#`'s barrier). Byte-array loop 46 ms to 3.1 ms, fill/freeze/sum 3.85 ms to 46 µs,
  CAS loop 1.03 ms to 124 µs; `suite`'s mergesort 2.2×, Shuffle 1.8×, CAS 11.6× faster than
  before. See "Arrays and Refs".
- [x] **10. `Universal.murmurHashUntyped`** (2026-10-04). A C walk of the closures feeds
  the same words to the same MurmurHash64A accumulator as the Haskell reflection and hash,
  fused from `VALU` and the foreign call; the library's seed and finalization hardcoded
  (Paul: "just hardcode the constants"); 21 sample values checked against Haskell at
  startup; maps left to the interpreter on purpose. Hashing `Some (i, "x")` 10000 times
  6.86 ms to 264 µs. Found and fixed on the way: a lazy memo update kept every module's IR
  alive (eager residency 6 GB to 0.5 GB), and a shutdown race in which the compile thread
  was inside LLVM when `exit` ran LLVM's destructors (an `atexit` guard). See
  "murmurHashUntyped, and a memory leak".
- [x] **11. A strict generator** (2026-10-05, Paul's todo). The code generator's text is
  `Unison.Util.Text`, its sequences `Unison.Util.Deque`, its pairs strict, every field of
  its state and output strict, `put` evaluates the state. Output byte-identical over 1210
  dumped modules; compile time of the eager test run 63.2 s to 61.2 s, GC time halved. See
  "A strict generator".
- [x] **12. The builtins checklist** ([builtins.md](builtins.md), 2026-10-04): every
  builtin by category and whether it is native, with the op or foreign function a missing
  one waits on; generated from the source by a script, so it stays true.

## Decisions made during M7

- **A strict structure before a clever fast path.** M6 had learned this for lists; M7
  applied it to text and bytes too, and to the generator. Native code can take apart and
  build a structure with no thunk in it, and the C helpers can be complete ports rather than
  fast paths with fallbacks, which is what removes the exits rather than reducing them.
- **Write the new structure beside the old one, benchmark, then swap** (Paul's plan for
  the rope, used for the Deque too). The benchmark decides; the swap is a change of import.
- **C helpers are ports, checked against the Haskell they replace at startup**, with a
  random test (`UNISON_JIT_STRESS=lists=N`, `texts=N`, `bytes=N`) for the long tail. A
  helper that can't decide a case exactly says "not handled" and the interpreter does it,
  so a helper is never wrong, only sometimes absent. If the startup check fails, the JIT is
  off.
- **The interpreter's semantics, bit for bit.** Floats are GHC's `Double` instances, not
  libm's conventions (`ceiling`'s wrapping arithmetic, `atan2`'s cases); bounds checks are
  the interpreter's wrapping arithmetic; number parsing takes only the forms the Haskell
  lexer would read the same way. The test transcripts compare output with the interpreter's,
  on both builds.
- **The modules whose constructors C reads are compiled `-O2 -funbox-strict-fields` in
  every build** (`Deque.Internal`, `Rope`, `Text`, `Bytes`), since `UNPACK` is ignored at
  `-O0` and the layouts would differ between the fast and optimized builds.
- **Allocation bumps `rCurrentAlloc`, not `Hp`.** `Hp` is a callee-saved register during
  the unsafe call native code runs in; the RTS keeps a separate block for C allocation and
  `allocate` uses it, so bumping it inline changes who moves the pointer and nothing else.
- **A copy of a callee is private and never installed**; its cell stays the original's.
  Recursive callees are not copied (a copy would be a second body gaining only the outer
  call). The criterion is estimated work per call, not code size (Paul).
- **The hash's constants are hardcoded, not derived.** The first version solved for the
  library's seed from two Haskell hashes at startup; Paul: the function won't change
  between versions, hardcode it once.
- **The generator is strict by construction**, not by inspection: strict fields, strict
  sequences, packed text, and `put` that evaluates, so that forcing the state forces all of
  it and no refactor can reintroduce a thunk over a module's text by accident.
- **Left as call-outs on purpose:** the Text patterns, compression, `Link.toText`,
  `Value.value` on its own, the typed `Universal.murmurHash` (it serializes first), maps in
  the untyped hash (the Haskell hash rebuilds the map with `fromDistinctAscList` and hashes
  that shape).

## Learnings and questions

- **The startup checks find real bugs on their first run.** The bytes check caught a layout
  that differed between the two builds (`UNPACK` at `-O0`); the list check caught a sample
  stored unevaluated; a field-less constructor compared by address failed when a module
  moved (one static closure per top-level binding that is just that constructor); planted
  bugs in the rope were caught by the ordinary check. A transcript whose output matches
  says nothing about whether the JIT was on: the log does.
- **GHC's optimized code trusts strict fields.** It reads through a strict field's pointer
  without checking its tag, so an untagged pointer the interpreter left on the stack (a
  static constant stored as itself) must be checked before native code stores it anywhere
  strict. The `-O0` builds never show this, which is why the optimized build has to be in
  the test matrix, and why there is a debug RTS over the optimized build.
- **An evaluated CAF is an `IND_STATIC` to a `BLACKHOLE`** whose indirectee is the value;
  following indirections from C has to know that case (the murmur probe's `DataG` sample,
  whose segment arrays GHC had floated to CAFs).
- **The cost of a C call per constructor was a fifth to a third of the allocation-heavy
  benchmarks.** Inline bumping took it back, and the budget costs nothing once it is an
  address compared by the same instruction.
- **Laziness leaks are found with `-hT`, not by reading.** 3.6 GB of `:` cells in an eager
  run was the IR of every module, kept alive by one lazy `Map.insertWith`;
  `atomicModifyIORef'` forces the map, not the value put in it. `String` IR at 24 bytes a
  character was most of what remained. The generator being strict throughout is the
  structural answer.
- **The fast build's interpreter is not the reference for float edge cases**: at `-O0` the
  RULES that make `Double -> Int` conversions saturate don't fire, so `ceiling 9.3e18`
  differs between the two builds of the interpreter itself. Edge cases are checked on the
  optimized build by hand; the transcript uses ordinary values.
- **`long double` is 64 bits on Apple arm64**, so the "nearest shortest digits" choice in
  `Float.toText` reads the exact decimal expansion instead.
- **Wrapper constructors of `Foreign` don't all have pointer tag 7**: `WrapArray` and
  `WrapByteArray` are early constructors with tags 1 and 2. The probe records the tag with
  the info pointer. A `Ticket` is a newtype over the value.
- **Process exit can run under a compile.** `hs_exit` doesn't wait for a thread in a safe
  foreign call, so `exit()` ran LLVM's static destructors while the compile thread was in
  its code generator, about one run in eight once re-entry batches flushed on a quiet
  period, which is exactly when a program finishes. An `atexit` handler waits for a compile
  in flight and parks the thread. A debugger slows exit enough that it never reproduced;
  the crash report did.
- **A refactor of a 4000-line generator is safe to do mechanically when the output can be
  diffed**: dump every module's IR before and after from optimized builds of both, mask the
  addresses, and compare.
- **Open.** Appending two large texts is slower on the finger tree than on the old rope
  (packing the inner digits at every level); `Json.toText` is 15 to 20% slower per document
  for reasons that didn't show in any part (Paul: the library should build through a
  builder); `on` mode's two timing regimes on `suite` (from M6) are still unexplained; the
  Text patterns, compression and the typed hash are the remaining call-outs that library
  code meets; two-stage batching (a holding area for fresh functions) is in the ideas doc
  and not done; eager mode makes no private copies.
